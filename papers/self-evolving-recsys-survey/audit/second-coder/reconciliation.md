## Codebook ambiguities behind these disagreements

1. **c3: test scored every generation but never used to select (EvoSkillRec).** The N text, "used during search or repeatedly", can be read as "computed" or as "consulted". Suggested wording: `N` only when test scores inform selection, promotion, stopping or which candidate is reported; logging test scores that the paper states were never consulted is still `Y`. A test-informed *post hoc* pick of the reported candidate (e.g. EvoSkillRec's "only P1 ... retains both improvements on the test set" for the co-evolution front) should be `P` when it touches only a secondary result.
2. **c8 mixes two dimensions:** *who* the comparator is (production / published / seed) and *how it was tuned* (tuned / untuned / P / NS). Self-EvolveRec (seed + shared defaults) and RecHarness (seed + tuning unstated) split the coders. Suggested precedence: (a) `P` if tuned on the reported split; (b) `tuned` / `untuned` if the tuning status is stated; (c) otherwise the comparator's identity (`production`, `published`, `seed`); (d) `NS` only if neither is known. This order also makes `NS` consistent across rows (the first coder used `NS` for RecHarness but `seed` for Feedback Contract and Evolving Semantic Indexes).
3. **c1 when the headline is a rate built on a recommendation metric (NOVA's EPR, the share of rounds with AUC gain ≥0.10 pp).** "other ... e.g. task success rate" literally fits, but the recommendation evidence is AUC. Suggested rule: code the recommendation metric that decides success. `other` is reserved for headlines with no recommendation metric underneath (rubric scores, coding-task pass rates).
4. **c6 when the non-LLM search is the reference calibration rather than a competing arm (Population Evolution's CMA-ES baseline HPO).** Clarify whether an HPO-tuned reference, against which all gains are measured, counts as a null at unmatched budget (`P`) or not at all (`N`). Also say whether "over the same space" excludes searches over a strict subspace (hyperparameters vs code). Both coders gave `P` to Self-EvolveRec's NAS baselines over a different operator space, which implies the space does not have to match for `P`.
5. **c5: is a larger or peer dataset `Y` or `P`?** The guide reserves `Y` for same-task selection-vs-held-out comparisons (val next to test) and lists "another dataset" under `P`. The README adds "scale". Population Evolution's systematic per-candidate source-vs-larger-scale results drew a `Y`. State explicitly that cross-dataset or cross-scale checks are `P` however systematic they are, or add a sub-rule if the survey wants to credit them.
6. **c9: `N` vs `P` when the paper shows the agent running test-split evaluation but also lists process gates (RankEvolve-HSTU).** Suggested rule: if the text shows the agent reading test labels or running or modifying test evaluation, code `N` whatever the process constraints. `P` is for constrained loops where access is merely not ruled out.
7. **c4: what counts as "repeats without spread".** Population Evolution mentions unreported "preliminary independent runs" and repeated reference evaluations. Say whether unreported or preliminary repeats qualify for `P`. The current text implies yes.

## Codebook ambiguities that caused these disagreements

1. **incident: a risk vs a reported event (AutoLR).** "Reports that the loop... inflated [the metric]" does not say whether a named and explained *mechanism* (the KEEP ratchet, "can create non-reproducible apparent progress") counts, or only a *documented instance*. Proposed rule: `Y` only when the paper documents at least one concrete case in which the loop's selected result was later shown to be inflated, gamed, leaked or bug-driven. A risk or mechanism the paper identifies without a case is `N`, and it goes in notes.
   - Note for consistency: A-MLE Sec 6.9 does report an instance ("the agent sometimes promoted a candidate based on a single seed when within-run variance warranted re-running"), yet both coders coded it `N`. The rule should also say whether a single-seed promotion counts as "inflation" without evidence that the gain then failed. Under the proposed rule it is `N` unless the paper shows the promoted gain did not hold.
   - The rule should also say whether incident covers controller or selection-protocol failures (AutoLR's ratchet comes from disabled noise calibration in deterministic code, not from the LLM), or only agent behaviour. The guide says "the loop itself", which covers both.
2. **c1 `none` vs `other`.** The first coder used `none` for "no recommendation-quality metric". The guide defines `none` as "no usable metric stated" and gives `other` for non-recommendation metrics. Proposed clarification: operational, throughput or success-rate metrics that support the headline are `other`. `none` is only for papers with no quantitative metric at all.
3. **c1 `online` when the abstract mixes offline and online claims (AutoLR vs Trajectories).** The guide should say: `online` when every *quantified* gain in the abstract is online. If any quantified offline gain is claimed (even descriptively), code that offline metric.
4. **c5 and online A/B of offline-selected candidates.** The guide lists "unseen users, a later period" under `P` but never names online A/B. Both coders read it differently in AgentX-Model and AutoLR. Proposed: an online A/B of candidates selected offline is `P`. For online-selecting loops the A/B is the selection data and does not count.
5. **c5 and side experiments.** The general "code the headline, not a side experiment" rule decided AgentX. Repeating it in the c5 row would prevent transfer studies on secondary tracks from being counted.
6. **c6 `P` scope.** The first coder gave `P` for human baselines, LLM-vs-LLM or memory ablations, and trivial rules (always-Reject). The guide's `P` covers only a non-LLM search with an unmatched budget, a "random" ablation where the LLM still proposes, or replay. Proposed: add "human, manual, LLM-vs-LLM and trivial decision-rule comparisons are `N`".
7. **c3 when the split is unnamed but selection = report (AgentX-Model).** Add: if the reported number is by construction the selection statistic (best-of-rounds or max over candidates), code `N` even when the split is not named. `NS` is only for when the relation between the selection data and the reported data cannot be determined.
8. **c2 when the paper defines "success" for a benchmark metric but not for the loop (Astar).** Code the signal stated for the loop that produced the headline. A success definition from an evaluation metric (S@k) or from training-data labelling should not be carried over to it.

## Google/YouTube c2: the selection decision and what follows

- **Two-stage funnel.** The Offline Agent scores candidates by validation loss (`compute_loss`, Sec 4.1.1 A-B) or by a long-watch-correlation proxy on evaluation data (`compute_eval`, Sec 4.1.1 C). It then sorts the Experiment Journal by this score.
- **Who keeps or rejects.** The Online Agent ranks the whole pool to pick the top K for live traffic, and it "must also consider the online metrics to produce a refined ranking" (Sec 4.2 (1)).
  - Candidates that drop out of the top K have their experiments terminated (Sec 4.2 (5)).
  - Humans give the final launch decision after reviewing online metrics (end of Sec 4.2).
- **Headline evidence.** The headline result is these launches, so the deciding signal is online.
- **Reward hyperparameters.** These launches never used an offline score: "without offline metrics, relying exclusively on the Online Agent's slow loop" (Sec 5.3.2).
- **What follows:**
  - c1 = `online`: the launch numbers are online only.
  - c3 = `na`: no offline test exists, and the loop selects online.
  - The validation-loss stage belongs in the design `signal_chain` (`offline>online*`, already recorded in design-evidence.md). It is not a c2 value.
  - Because this row moves from offline-selecting to online-selecting, the strata counts in the survey change: offline-selecting 17 -> 16 and online-selecting 9 -> 10. Rerun `summarize.py` if this is accepted.

## Codebook ambiguities behind these disagreements

1. **c2 with multi-stage funnels.** Several loops filter offline and then select online, among them Google/YouTube and EvoRec.
   - The guide does not say which stage to code.
   - Proposed rule: code the last gate that keeps or rejects among several candidates before the headline result. Record earlier filters in notes or `signal_chain`.
   - A single online A/B that only confirms one already-selected model is not selection, as with EvoPilot and EvoRec. It counts for c5, not c2.
2. **c1 when the abstract's headline mixes offline and online.** The guide should say which one to code when the abstract leads with launches or online lifts.
   - Proposed rule: code the metric behind the numbers in the headline sentence.
   - "only an online metric" should mean that no offline number is reported for the headline candidates. Offline numbers in ablations do not count.
3. **c1 when the candidate set must be inferred.** RecEvolve never writes "evaluation uses in-batch negatives", but its reward-hack explanation implies it.
   - The guide should say whether an implication from the paper's own mechanism counts as "stated".
   - Proposed rule: yes, when the paper's own text entails it. Note "inferred" in the notes.
4. **c5 and online A/B of the selected model.** The first coder coded an online A/B as P for Google/YouTube and EvoPilot, but as N for EvoRec and RecEvolve.
   - The guide should say explicitly that an online A/B of the selected candidate is P: unseen users, later period.
   - It should also say that designed but unreported confirmations count as N (PILOT).
   - Checks of a proxy or predictor rather than of the selected candidates also count as N (DMRL Fig. 4).
