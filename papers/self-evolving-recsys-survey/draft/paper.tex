\title{Self-Evolving Recommender Systems: A Survey and an Evaluation Audit}

\author{Shanglin Yang}
\affiliation{\institution{Independent Researcher}\country{USA}}
\email{kudoysl@gmail.com}

\author{Zhan Shi}
\affiliation{\institution{Santa Clara University}\city{Santa Clara}\state{CA}\country{USA}}
\email{ashi2@scu.edu}

\begin{abstract}
Large language model (LLM) agents now improve recommenders the way engineers do: they edit the model's configuration
or code, train the result, and keep what the evaluation favours. By 22 October 2026 we found 34 such loops (one known only from a blog post), from
open-source harnesses to systems at Google, Meta, Amazon, Alibaba, Kuaishou and others. We organise them by what the
loop changes, who proposes the change, and which signals decide whether it survives. We then audit how 27 of them
report their evaluation on eight criteria, and release the coding with its evidence. The reporting is thinnest where
an optimiser most needs it. Of the 16 loops that select candidates offline, none reports the spread over repeated
sessions, eight do not say which data select the candidates (seven of these confirm the kept candidate online), and two state that the test set was used only once. Of
the 10 loops that select by online experiment, so that the reported effect is the best of several rounds, none fully
corrects for testing many rounds and one confirms its chosen candidate in a fresh experiment (coded by one author). Four loops report shortcuts in their own evaluation, such as a metric inflated
by a changed batch size in an exploratory session. The counts describe what the papers report, as coded by the authors, not independently. We turn them into a
proposed two-tier reporting checklist whose minimum tier asks authors only to state what they did.
\end{abstract}

\keywords{recommender systems, LLM agents, AutoML, program evolution, evaluation, reproducibility}

\section{Introduction}
%=====================================================================

Recommender models have long been improved by a loop that engineers run by hand: propose a change, train, compare
offline, and launch the winners into an online experiment. Automating parts of this loop is an old goal. Neural
architecture and embedding search, mostly for click-through-rate (CTR) prediction
models~\cite{song2020autoctr,liu2020autofis,zhao2020autoemb,zhang2023nasrec}, and loss search~\cite{li2022autolossgen}
automated the choice inside a space that a person had written down~\cite{zheng2022automl}. What changed in the loops we found, nearly all from 2026 (our arXiv screen began in 2025), is that the proposer became an LLM agent that
writes code. Following FunSearch~\cite{romeraparedes2023funsearch}, AlphaEvolve~\cite{novikov2025alphaevolve} and
open implementations such as OpenEvolve~\cite{openevolve} and ShinkaEvolve~\cite{lange2025shinka}, agents now edit
the model, loss and training code of recommenders directly. Google reported such a loop for YouTube
ranking~\cite{wang2026selfevolving} and Self-EvolveRec released an open harness~\cite{kim2026selfevolverec} in February
2026; within months, open harnesses such as RecHarness~\cite{ling2026recharness} and systems at Meta~\cite{meta2026rea,li2026autorecsys}, Alibaba
\cite{mu2026evorec,hu2026astar}, Kuaishou~\cite{lao2026agentx,yang2026sragent,zhuang2026trajectories}, Tencent
\cite{liu2026nova,ao2026recsysfactory}, NetEase~\cite{zhang2026autolr} and others followed.

These systems are optimisers, and an optimiser exploits whatever its objective rewards. A loop that evaluates
hundreds of agent-written candidates on one validation set and keeps the maximum is the setting in which the known
weaknesses of recommender evaluation---sampled metrics~\cite{krichene2020sampled}, temporal
leakage~\cite{ji2020leakage}, untuned baselines~\cite{dacrema2019progress,rendle2020ncf}, and the reuse of a holdout
for adaptive decisions~\cite{dwork2015reusable,blum2015ladder}---are, we expect, the ones most readily turned into reported gains. The agent
also controls the code that produces its score. Four of the audited loops and one comparison point report incidents in
which a candidate raised the metric, or would have, without a real improvement; in all but EvoPilot, whose paper does
not say who chose the leaky evaluation date, the agent produced it. For example, RecEvolve's agent, in an exploratory session, inflated its proxy metrics by shrinking the batch size, and with
it the number of in-batch negatives~\cite{pan2026recevolve}, and an AI co-scientist for search ranking produced
implementations that ``improved $\mathcal{M}$ while being wrong (e.g., silently increasing model
size)''~\cite{wu2026coscientist}. Four incidents cannot estimate how often this happens, and our audit does not measure overfitting or gaming rates:
it measures what papers report about the safeguards against them. Figure~\ref{fig:loop} shows the loop these systems share and the points where the
evidence for a gain can fail.

\input{figs/loop}

No existing survey covers this development (\S\ref{sec:background} compares the nearest ones), and no audit has
asked how its gains are evaluated. This paper does both, as a dated snapshot with a cut-off of 22 October 2026. Our
contributions, in order of weight, are:
\begin{enumerate}
\item \textbf{An evaluation audit} (\S\ref{sec:audit}). We code the 27 recommendation loops that keep or reject
trained candidates on eight criteria, report loops that select offline and loops that select online separately, give
a range for every count that rests on unstated practice, and catalogue the shortcuts agents found. Every code and its
evidence are released.
\item \textbf{A proposed reporting checklist} (\S\ref{sec:protocol}). Its minimum tier asks authors only to state what
they did; its recommended tier costs compute. Each item maps to an audit criterion, and we read the audit coding
against it as a retrospective proxy.
\item \textbf{A taxonomy and synthesis} (\S\ref{sec:taxonomy}--\S\ref{sec:systems}) that separates what the loop
changes, who proposes the change and which chain of signals decides whether it survives, and records the loops'
recurring designs and what they actually kept.
\end{enumerate}

\paragraph{Findings at a glance.} The counts are over the 27 coded loops, in two strata (\S\ref{sec:audit}); each
is explained, with its range and reliability, in \S\ref{sec:audit}.
\begin{itemize}
\item F1: 3 of the 10 offline-selecting loops that report ranking metrics rank the full catalogue (3--7 if read either way).
\item F2: 8 of the 16 offline-selecting loops do not state their selection data, so 4--12 may select on the data they report.
\item F3: 2 of 16 state test-once use (2--10).
\item F4: 0 of 16 report spread over repeated sessions.
\item F5, F6: 1 of 16 checks its selected candidates on held-out data of the same task, and 3 of 16 compare against an equal-budget non-LLM search.
\item F7: 4 of 27 report shortcuts in their own evaluation.
\item F8: the 17 reported lifts on a broad online metric range from +0.052\% to +4.86\%.
\item F9: of the 10 online-selecting loops, 0 correct across rounds (1 in part) and 1 confirms afresh (4 in part).
\end{itemize}

\section{Scope and Survey Method}\label{sec:method}
%=====================================================================

\paragraph{Definition.} We call a recommender system \emph{self-evolving} when an automated proposer changes some
part of it, the changed system is evaluated, and the evaluation decides which changes are kept, repeatedly and
without a human choosing each change. As a codable rule: a loop is in scope when an evaluation result decides which
candidates survive and a person can at most gate, approve, veto or roll back what it kept, or review it at checkpoints;
it is out of scope when a person chooses which candidates to keep without an evaluation deciding first. This includes systems whose proposer is a search algorithm over a fixed space (background,
\S\ref{sec:background}), but our focus is on LLM proposers.

\paragraph{Inclusion.} We include (i) systems that change a recommender's or ranker's configuration, features, code or
components under an evaluation loop; (ii) agentic or LLM recommenders whose policy, memory, skills, prompts or weights
improve from feedback they generate; and (iii) benchmarks, environments and surveys for these. Only (i) is audited.
The boundary is the selection step: in (i) a trained candidate recommender is evaluated and kept or rejected, which is
what the audit criteria test, whereas in (ii) the recommender's own state is updated continuously from feedback it
mostly generates itself, with no separate candidate to accept. We therefore catalogue (ii) as adjacent work
(\S\ref{sec:l4}) but do not audit it. A loop qualifies for (i) whatever the size of the change, so loops that change
only configuration values, such as GEARS's segment-level treatment policies chosen by online experiments, are audited. We exclude LLM
recommenders without a self-improvement loop, conversational recommendation in general, and general
hyperparameter-optimisation libraries. We also exclude methods that use an LLM once as a fixed training signal for a
conventional recommender (such as offline LLM pairwise supervision applied only where a gate on history length,
item popularity and model uncertainty predicts it is reliable~\cite{shi2026selective}), and methods that evolve the recommendations rather than the recommender (such as
QD-Rec's quality--diversity archive of items and hypotheses~\cite{ishida2026qdrec}). Finally, we exclude continual-learning methods
that call themselves self-evolving but have no proposer or selection step, such as LION's sparse key--value memory
for a generative recommender~\cite{lin2026lion}. Seven studies outside recommendation are included as comparison points because they
inform evaluation: learning to rank~\cite{patel2026evorank}, search ranking~\cite{wu2026coscientist}, e-commerce search
strategy~\cite{wang2026pear}, lexical retrieval~\cite{nian2026rankevolveir}, generative document
retrieval~\cite{nian2026semanticindex}, lifetime-value (LTV) prediction~\cite{wu2026agentltv}, and a controlled study of
agent feedback on public CTR and learning-to-rank (LTR) data~\cite{yao2026feedbackcontract}.

\paragraph{Search protocol.} The cut-off date is 22 October 2026. We started from keyword searches over arXiv,
OpenAlex and Semantic Scholar (``self-evolving recommender'', ``LLM agent recommender model optimisation'', ``agentic
harness recommender'', ``LLM-driven architecture search CTR'' and survey queries). We then walked the reference lists of
the 2026 systems (RecHarness, EvoRec, AgentX-Model, RecEvolve) and of the agentic-recommender roadmap backwards and
their titles forwards, and finished with about thirty full-text arXiv phrasings combined with company names. Generic
keyword search returned mostly unrelated ``agent for $X$'' papers (\S\ref{sec:threats}). This first sweep yielded 22 of the audited systems
and five comparison points. A second sweep then ran 190 further arXiv queries (817 new candidates, all screened by
title; the last 31 repeat the company-name search on abstracts, logged query by query). It also enumerated 13 ACM proceedings volumes through OpenAlex (RecSys, KDD, SIGIR and WWW 2025--2026 including the
WWW companions and the February KDD 2026 cycle, CIKM 2025 and WSDM 2026; 6{,}874 records filtered by a title keyword pattern, and the 536 hits screened by title), followed
forward citations of 16 seed systems in Semantic Scholar, and searched industry engineering blogs. It found nine
further candidates: five entered the audit as core systems, two as comparison points, and two are known only from
their abstracts (\S\ref{sec:audit}). CIKM 2026, DBLP and OpenReview could not be searched
automatically.\footnote{OpenReview was covered only by manual web searches, and its PDFs were blocked.} Titles were screened by a single screener with LLM assistance (for the ACM volumes, after a keyword filter), not in
duplicate. The recall of the screen is therefore not measured, and individual title decisions were not logged.\footnote{The keyword filter, every second-sweep query with its hit
count and the per-volume counts are released with the search log, but the list of candidate identifiers was not saved, so the screen can be re-run from the logged queries but not checked record by record (arXiv's index has changed since).}
Only hits dated 2025 or later were screened, so the second sweep cannot have found earlier systems; Appendix~\ref{app:provenance} gives the per-query hit counts and the bibliography checks. Table~\ref{tab:flow} counts systems for the first sweep, which was logged as the systems it found, and records only for the second.

\paragraph{Audit procedure.} We coded nine criteria (Table~\ref{tab:codebook}), eight of them scored and C7 as free text, for each configuration- or code-level system, in six steps.
(1)~Extraction: LLM agents read the full text (arXiv HTML or PDF, including appendices) and extracted a quote for each cell.
(2)~First coding: the first author coded each cell from that quote and its context, checked against the paper text but without a full reading of every paper.
(3)~Verification: LLM verification passes, reviewed by the authors, re-checked the cells and the cited sentences.
(4)~Second coding: a second author coded every core system by hand from the full text (without an LLM, by the coder's own account), not independently.
(5)~Reconciliation: LLM agents drafted a resolution for each disagreement, which the authors reviewed.
(6)~Online gates: one author coded the online-experiment items of F9, and a blind LLM re-coding checked them.
Table~\ref{tab:whocoded} and \S\ref{sec:threats} say who coded what, and Appendix~\ref{app:provenance} gives the full history. We audit what the papers report: a criterion is coded ``not stated'' when the
paper does not say, which is different from ``no''. Each ``yes'' or ``partial'' cell is backed by a verbatim quote of at most 25 words
with a section pointer. Since no quote can show an absence, most ``no'' and ``not stated'' cells give the section searched or a short reason instead. The data file and the evidence are released\footnote{\url{https://github.com/shangliy/recforge/tree/master/papers/self-evolving-recsys-survey/audit}}
so that the coding can be checked and corrected. For systems whose launch decision is an online experiment, we read the offline criteria as describing the
offline screen, and assess the launch evidence separately (R9 in \S\ref{sec:protocol}).

\section{Background}\label{sec:background}
%=====================================================================

\paragraph{Related surveys.} Surveys of LLMs for recommendation treat the LLM as a feature encoder,
a ranker or a generator~\cite{wu2023llmrecsurvey,lin2023recsysllmsurvey}, and surveys of LLM agents for recommendation
treat the agent as the recommender, a conversational interface or a user simulator~\cite{peng2025agentsurvey,zhang2025agentsearchsurvey,
huang2025fmsurvey}. Surveys of self-evolving agents treat the agent's own prompts, memory, tools or weights as the
object that evolves, and mention recommendation at most in passing (a two-sentence mention of self-optimised fine-tuning and a recommendation task in a benchmark it describes
in~\cite{gao2025selfevolvingsurvey}, none in~\cite{fang2025selfevolvingsurvey}).
The most recent roadmap for agentic recommender systems mentions the ``agent as engineer'' direction in one clause of its task list, which cites AgentX and the Google loop~\cite{lin2026roadmap}. The most recent peer-reviewed
survey of agentic recommenders organises 47 studies by where the agent sits in the serving workflow, not by what
changes the recommender~\cite{xu2026scoringworkflow}; we judged it from its abstract and resolved reference list, since we could not obtain the full text. A general survey of how automated research is evaluated covers
no recommender system~\cite{zhang2026autoreseval}. Closest to our audit, a concurrent controlled study shows on CTR and
learning-to-rank data that exact validation feedback lets a coding agent overfit the validation split, and that a
feedback contract with a quarantined test set removes the spurious gain on a task with no signal~\cite{yao2026feedbackcontract}. Beel et al.\ call for autonomous recommender-systems research labs and for benchmarks
to evaluate them~\cite{beel2025autoreclab}. RMD-Bench~\cite{peng2026population} fixes protocols for cross-dataset and
cross-scale discovery and ExecML-HSTU~\cite{chen2026rankevolve} measures whether agents' edits execute correctly, but no
shared benchmark yet compares evolvers under a sealed test, full-ranking evaluation and
equal-budget null controls.

\paragraph{Search-space AutoML for recommenders.} Automated machine learning (AutoML) for recommenders searched for feature-interaction structures
(AutoCTR~\cite{song2020autoctr}, AutoFIS~\cite{liu2020autofis}), embedding dimensions (AutoEmb~\cite{zhao2020autoemb},
AutoDim~\cite{zhao2020autodim}), whole architectures with a weight-sharing supernet (NASRec~\cite{zhang2023nasrec}),
compact attention-based sequential models under resource constraints (DNS-Rec~\cite{zhang2024dnsrec}), embedding
tables (OptEmbed~\cite{lyu2022optembed}) and loss functions (AutoLossGen~\cite{li2022autolossgen}); two surveys
cover this line~\cite{zheng2022automl,chen2022automlrecsurvey}. Each method can only return a design that its space contains. Evaluation is mostly
validation logloss or AUC on public CTR data, or standard rating and sequential benchmarks, with standard splits. Even
in this setting, careful re-evaluation of architecture search found that the search phase often added little over
random sampling and that the evaluation protocol dominated reported differences~\cite{li2019randomnas,yu2020searchphase,
yang2020nashard}. The community answered with tabular and surrogate benchmarks that make equal-budget comparisons
cheap~\cite{ying2019nasbench101,dong2020nasbench201,eggensperger2021hpobench} and with a best-practice
checklist~\cite{lindauer2020bestpractices}. The LLM loops below inherit these problems with a larger, open-ended space
and with control over the evaluation code.

\paragraph{LLM program evolution and ML-engineering agents.} FunSearch~\cite{romeraparedes2023funsearch} and
AlphaEvolve~\cite{novikov2025alphaevolve} pair an LLM that proposes code with an automatic evaluator and an archive of
programs, a pattern that AutoML-Zero had applied to whole learning algorithms with random mutation instead of an
LLM~\cite{real2020automlzero}. Open systems followed: OpenEvolve~\cite{openevolve}, ShinkaEvolve~\cite{lange2025shinka} and
DeepEvolve~\cite{liu2025deepevolve}. LLM-guided evolution was applied earlier to neural architecture search (NAS)
(EvoPrompting~\cite{chen2023evoprompting}, LLMatic~\cite{nasir2023llmatic}, GPT-NAS~\cite{yu2023gptnas}, and GPT-4 as a
NAS proposer~\cite{zheng2023gpt4nas}), to heuristics~\cite{ye2024reevo}, reward functions~\cite{ma2023eureka} and
scientific equations~\cite{shojaee2024llmsr}, and to prompts and LLM pipelines as optimisation targets
(OPRO~\cite{yang2023opro}, EvoPrompt~\cite{guo2023evoprompt}, DSPy~\cite{khattab2023dspy},
TextGrad~\cite{yuksekgonul2024textgrad}); the last are the general form of the L4 prompt loops of
\S\ref{sec:l4}. ML-engineering agents---AIDE~\cite{jiang2025aide},
MLE-STAR~\cite{nam2025mlestar}, R\&D-Agent~\cite{yang2025rdagent}, AIRA~\cite{toledo2025aira}, DS-Agent~\cite{guo2024dsagent},
AutoML-Agent~\cite{trirat2024automlagent}, Agent Laboratory~\cite{schmidgall2025agentlab} and the AI
Scientist~\cite{lu2024aiscientist,yamada2025aiscientistv2}---apply the same pattern to whole training pipelines, and
recent work optimises the agent harness itself~\cite{lou2026autoharness,lee2026metaharness,xu2026harness2,wong2025confucius}. Their
benchmarks contain at most one recommendation task: MLE-bench includes the H\&M fashion-recommendation
competition~\cite{chan2024mlebench} and MLRC-Bench a next-product-recommendation task~\cite{zhang2025mlrcbench}.
MLRC-Bench shows agents only the development split and scores the best development snapshot once on test, whereas
MLGym's \texttt{validate} command returns test-set metrics during the session~\cite{nathani2025mlgym}. Broader
benchmarks for data-science and research agents~\cite{chen2024scienceagentbench,jing2024dsbench,qiang2025mledojo,
starace2025paperbench,chen2025mlrbench,kon2025expbench} contain no recommender-model task, and an independent evaluation
of an AI-scientist system found its claimed results hard to reproduce~\cite{beel2025aiscientist}.

\paragraph{Generative recommenders.} HSTU~\cite{zhai2024hstu} and TIGER~\cite{rajput2023tiger} recast recommendation
as sequence generation over item IDs or semantic IDs, and OneRec unifies retrieval and ranking in one generative model
that is further aligned on its own samples, first by iterative direct preference optimisation (DPO)~\cite{deng2025onerec} and then by on-policy
reinforcement learning (RL)~\cite{zhou2025onerectech,zhou2025openonerec}. These models add new objects that a loop can evolve: tokenisers, codebooks,
decoding procedures and generative losses.

\paragraph{Evaluation methodology.} Tuned simple baselines beat many published neural
recommenders~\cite{dacrema2019progress,rendle2020ncf}; a loss change alone can reorder SASRec~\cite{kang2018sasrec} and
BERT4Rec~\cite{sun2019bert4rec,klenitskiy2023dross}, and BERT4Rec's reported advantage depends on much longer
training~\cite{petrov2022bert4rec}; sampled metrics are inconsistent with full-ranking metrics and
can reverse model rankings~\cite{rendle2019sampled,krichene2020sampled,hidasi2023flaws}; leave-one-out splits that
ignore the global timeline leak future information~\cite{ji2020leakage,hidasi2023flaws}, and the split choice changes
rankings~\cite{meng2020splitting}. Systematic re-examinations found that most neural recommenders could not be reproduced or were beaten by tuned
simple baselines~\cite{dacrema2021troubling}, that evaluation choices varied widely across papers~\cite{sun2020rigorous},
and that with untuned baselines any proposed model can win~\cite{shehzad2023everyone}. Libraries and open benchmarks such as RecBole~\cite{zhao2021recbole}, Elliot~\cite{anelli2021elliot},
DaisyRec~\cite{sun2022daisyrec}, BARS~\cite{zhu2022bars} and FuxiCTR~\cite{zhu2021fuxictr} standardise protocols for
human-designed models. For adaptive reuse of a holdout, theory predicts overfitting~\cite{dwork2015reusable,
blum2015ladder}; empirically, a meta-analysis of 120 Kaggle competitions found little~\cite{roelofs2019metaanalysis}. For LLM
loops specifically, keep-if-better acceptance is selection under noise, with selection-set scores well above held-out
accuracy when the selection set is small~\cite{hu2026winnerscurse}, and best-of-$N$ runs produce apparent gains from
selection alone~\cite{grover2026luckyruns}. For LLM research agents, the scarcity of overfitting has been tied to how
compressible their successful strategies are~\cite{bertran2026whatfits}, and AI-scientist systems hide post-hoc selection, leakage and metric
misuse~\cite{luo2025pitfalls}. Beyond recommendation, results depend on seeds and on the budget spent tuning
them~\cite{henderson2018deeprl,bouthillier2021variance,dodge2019showyourwork}, leakage is a recurring cause of
irreproducible ML-based science~\cite{kapoor2023leakage}, and agent benchmarks are sensitive to cost, budget and
task-setup flaws~\cite{kapoor2025agentsmatter,wijk2024rebench,huang2023mlagentbench,zhu2025abc}. For online
selection, the relevant tools are variance reduction with pre-experiment data~\cite{deng2013cuped}, interleaving for
more sensitive ranking comparisons~\cite{chapelle2012interleaving}, sequential tests that stay valid under repeated
looks~\cite{johari2015alwaysvalid}, and off-policy replay and doubly robust estimation for evaluating policies on
logged data before an experiment~\cite{li2011replay,dudik2011doublyrobust}.
We return to this tension in \S\ref{sec:audit}. Figure~\ref{fig:timeline} places these precursors next to the
2026 systems.

\section{A Taxonomy}\label{sec:taxonomy}
%=====================================================================

A recent blueprint for self-evolving agentic recommenders distinguishes reinforcement-learning evolution in defined
action spaces from LLM generation and selection in open design spaces~\cite{hu2026rethinking}. We describe a loop by
three separable choices: what it changes, who proposes the change, and which signals decide
whether the change survives (Table~\ref{tab:taxonomy}). Separating the proposer from the object avoids a conflation
that is easy to make, in which ``AutoML'' names a kind of proposer (search over a written-down space) but is listed as if
it were a kind of object.

\paragraph{Axis 1: the evolved object.}
\textbf{L1 configuration}: values in an existing configuration---hyperparameters, fusion weights, retrieval budgets,
thresholds, strategy parameters.
\textbf{L2 code}: executable model, loss, training or feature code, however small the edit.
\textbf{L3 generative components}: semantic-ID construction, item tokenisers and vocabularies, and decoding of a
generative recommender; L3 takes precedence when such a component is changed through configuration or code.
\textbf{L4 agent policy}: the prompts, memory, skills or weights of a recommender that is itself an LLM agent.
A loop that changes several objects carries several labels (L1+L2 when an agent edits both learning rates and
model code); 10 of the 27 audited loops do.

\paragraph{Axis 2: the proposer.}
An \emph{enumerated space}: classical search (grid, Bayesian optimisation, evolutionary or differentiable
architecture search) over options a person wrote down; this is search-space AutoML. An \emph{LLM}: a language model
writes the change, free-form or inside human-defined edit arms. A \emph{hybrid}: a classical selector chooses the
direction and an LLM writes the change (RecHarness's Thompson sampling over edit arms~\cite{ling2026recharness}), or an
LLM steers a classical search (Sortify's controller around Optuna~\cite{cheng2026sortify}). A \emph{learned proposer}:
a model trained on the system's own history proposes the next direction (Astar~\cite{hu2026astar}; we also count DMRL here, whose RL-trained LLM writes the skill document a frozen LLM agent follows, coded \texttt{learned+llm} in the data). Orthogonal to
these, a loop is \emph{meta}-evolving when it changes the proposer's own instructions, tools, skills or weights and
reuses them later; keeping an archive or a log of past results does not count. By this rule 11 of the 27 audited loops
are meta-evolving (Table~\ref{tab:design}). We flag separately a loop whose \emph{evaluator} evolves, that is,
whose feedback code, objective or reward model changes during the run: Self-EvolveRec's diagnosis tool co-evolves with
the model, Sortify recalibrates its search objective each round, and Astar recalibrates its reward model. An evolving
evaluator is a selection problem of its own, because the measure that accepts candidates changes with them.
The first two axes are descriptive; Table~\ref{tab:crosstab} relates them to the audit outcomes.
The object of evolution coincides with the stratum: eight of the nine configuration-only loops select online, and 15 of
the 18 loops that edit code or models select offline, which is where the offline criteria bite. Proposer type and
meta-evolution show no clear pattern in the offline criteria; the groups are small, and the table describes the
corpus rather than estimating an effect. All four reported incidents come from loops that edit code, which with four incidents is an observation, not a rate.

\paragraph{Axis 3: the selection chain.}
A candidate passes an ordered chain of signals, one of which decides inside the loop. \textbf{Self}: an LLM critic,
council, auditor or simulator judges the candidate before or instead of measurement. \textbf{Proxy}: a reduced-scale
screen, a proxy model, a training-loss curve or a replay. \textbf{Offline}: evaluation of the trained candidate on
held-out data. \textbf{Online}: an A/B experiment. Industrial loops typically chain several, for example
self$\rightarrow$offline$\rightarrow$online; whether the offline split is a validation or a test split, and whether it is
stated, is a property of the evaluation that we audit (\S\ref{sec:audit}), not of the design.

Each signal fails in a characteristic way, and the failures are of two kinds~\cite{manheim2018goodhart}. \emph{Regressional}
failures come from selecting the maximum of noisy estimates: an offline split reused over hundreds of candidates rewards
noise~\cite{dwork2015reusable}, a proxy ranks candidates differently from the full model, an online round selected as best
overstates its effect~\cite{lee2018winnerscurse}, and an LLM judge from the same model family as the proposer shares its
errors. \emph{Adversarial} failures come from an optimiser that changes what is measured: an agent that can edit the
evaluation code, the batch size of an in-batch metric or the evaluation date can raise the score without improving the
recommender~\cite{skalse2022rewardhacking,zhong2026impossiblebench}. The audit checks the first kind with C2--C6 and the
second with C9.

\section{What the Systems Share}\label{sec:systems}
%=====================================================================

Appendix~\ref{app:catalogue} describes each system, level by level; this section records what the systems share
and what their loops kept.

\subsection{Recurring designs}\label{sec:designs}
Table~\ref{tab:design} places the 27 audited loops on the three axes and adds the role of humans; the released
\texttt{design.csv} also records each loop's memory, acceptance rule, guards and LLM, with evidence. Four patterns
recur.

\emph{Where the chain ends.} Eight loops end at an offline evaluation: three open harnesses
(Self-EvolveRec, VirtualMLE, EvoSkillRec) and five industrial research loops whose papers report offline results, or in
Auto-RecSys's case only operational ones (A-MLE, Auto-RecSys, RankEvolve-HSTU, Population Evolution, Amazon
AutoResearch). The other 19 pass candidates to an online experiment, and 14 of them involve humans: eleven approve
launches, rounds or candidates, and three check or intervene. The two ends are exposed
to different failures. A loop that ends offline controls the code and data that produce its final number, so the
adversarial failures matter most; a loop that ends online cannot change the measurement easily but selects on
expensive, noisy experiments, so the regressional ones do.

\emph{LLM review before measurement.} Eight loops make an LLM critic, council or auditor a gate that every
candidate must pass before it is measured (Table~\ref{tab:design}, chains starting with S); others, such as RecEvolve,
A-MLE and RankEvolve-HSTU, use LLM critics to rank or filter ideas. These gates are cheap and catch invalid edits---NOVA's
verifier rejects target leakage~\cite{liu2026nova}---but they add a selection stage whose judge often comes from the
same model family as the proposer, the condition under which a self-generated signal is least
reliable~\cite{gao2023overoptimization,yang2026ideationgoodhart}.

\emph{Hybrids that keep a classical selector.} Six loops leave the choice of direction or the numeric search to a
classical method and use the LLM to write or steer: Thompson sampling over edit arms (RecHarness), an evidence-weighted
selector (AutoLR), typed operators over a skill library (EvoSkillRec), Optuna (Sortify), Pareto enumeration (GEARS) and
a deterministic action enumerator (PILOT). Because the classical part already defines a space, these designs could
run an equal-budget null over it with little extra code; only EvoSkillRec reports one (against NASRec), and RecHarness's
random arm router still applies LLM-written edits.

\emph{Humans in the loop.} Only nine papers describe no human role in the loop. Five have a person approve or review each
round or candidate (AgentX, AgenticRecTune, A-MLE, EvoPilot, A/B Agent). Under the rule of \S\ref{sec:method} this does not remove
them from scope, because the person approves or vetoes what an evaluation kept. It does mean that their reported gains are those of a human--agent
system.

\subsection{What the loops kept}\label{sec:kept}
Three papers report no kept edit (Auto-RecSys, AutoLR, DMRL), Astar reports only proposals in case
studies, and A-MLE only technique families. The other 22 name the changes their loops kept or launched, and we coded
the 87 edit descriptions they give by kind (a description that groups several updates, such as SR-Agent's ten, counts once) (\texttt{design.csv}; the tally is generated by \texttt{summarize.py}). The eight configuration-only loops that name kept edits (DMRL, the ninth, names none) kept strategy parameters (17 of their 20 edits): fusion
weights, sorting-formula coefficients, retrieval budgets, thresholds. The fourteen code-level loops kept most
often architectural changes (29 of 67) and loss or objective changes (12), then optimiser and
schedule settings (8), data and negative sampling (6), and a few strategy, regularisation, capacity,
feature and other changes. As far as the papers report their kept edits (which they chose to describe, and which one author coded), we hypothesise
that code-level loops do more than expensive hyperparameter optimisation (HPO). R5's null would test this hypothesis, and it matters for the choice of null control (R5 in
\S\ref{sec:protocol}): an equal-budget HPO run over the changed knobs is a necessary but not a sufficient null for them, and R5's recommended null for a code-level loop mutates its code at random.

Many of the named edits are established techniques transplanted into a particular model: InfoNCE losses and hard
negatives~\cite{kim2026selfevolverec,mu2026evorec,chandran2026autoresearch}, DCN-V2 layers and cosine learning-rate
decay~\cite{pan2026recevolve}, SwiGLU feed-forward blocks~\cite{cao2026virtualmle,liu2026nova}, gated
paths~\cite{wang2026selfevolving}, RMSNorm~\cite{zhuang2026trajectories}, expert pools~\cite{yang2026agentxmodel} and
checkpoint averaging~\cite{peng2026population}. This is useful engineering, and finding which known technique helps a
given production model is much of what human model iteration does. It also suggests a null that no paper runs: a
scripted sweep over a catalogue of known techniques at the same budget. One caveat applies: papers report the edits they find interesting, not all kept
edits.

\section{How Are Self-Evolving Recommenders Evaluated? An Audit}\label{sec:audit}
%=====================================================================

\paragraph{Audited set.} We audited the 27 recommendation loops at levels L1--L3 that keep or reject candidates by
evaluation, and the seven comparison points of \S\ref{sec:method}, in two strata: 16 \emph{offline-selecting} loops,
which decide on offline or proxy evaluations (some later confirm online), and 10 \emph{online-selecting} loops, which
decide on A/B experiments and are assessed on the design of those experiments. The remaining loop, Auto-RecSys, reports only operational
outcomes and makes no accuracy claim. Six in-scope systems are not yet coded: four were recognised only after the second coding was returned, and two are known only from abstracts. Appendix~\ref{app:provenance} names them and the borderline systems read but not counted. Every count below is about the 27 coded loops. Table~\ref{tab:audit} gives the coding, Figure~\ref{fig:auditbars} summarises it, and Table~\ref{tab:headline} states each headline count once, with its denominator, range, coder, agreement and how far it could move if the six were added. Every coded count is recomputed by script from the released data, but a few judgement-based sets are listed in the script rather than stored as data columns.\footnote{The audit, crosstab, sensitivity and proxy-check tables and the figure are generated from them by \texttt{summarize.py}; the value columns of the headline table, Table~\ref{tab:headline}, are printed by \texttt{summarize.py --headline}, which names the judgement-based sets (agent-introduced incidents, stated catchers, the same-space and strict null controls) and reads the F8 lift range from \texttt{f8-lifts.md}; the design table, Table~\ref{tab:design}, was assembled by hand from the data files (the kept-edit tally is generated by \texttt{summarize.py} from hand-coded fields).}

\paragraph{How to read the counts.} We state the limits of every count here once, and do not repeat them.
(i)~A count describes the coded corpus, not the field, and the corpus comes from a citation-led search whose recall was
not measured (\S\ref{sec:threats}). (ii)~It describes what the papers report: ``not stated'' is not ``no'', so where a
count rests on such cells we give the range it would span if each were read either way. (iii)~It rests in effect on
one author's reading. Two authors coded the 27 loops, but not independently, and the released codes follow the second
coder's sheet in 236 of 243 cells; no rater outside the team was involved. We therefore tag F1--F3, F7 and F9
\emph{provisional}, and F5, F6 and F8, which rest on low agreement or on one coder, \emph{descriptive}: we report their
evidence and draw no conclusion from the counts. F4's zero needs no judgement. Table~\ref{tab:headline} gives each
count with its denominator, range, coder and agreement, and how far it could move if the six uncoded loops were added.
Every credited cell is quoted in the released evidence, and a blind re-coding of the 48 cells behind F2--F4 by an
outside rater is the first check we invite. Figure~\ref{fig:auditbars} summarises the coding, and the findings follow.

\paragraph{F1 (provisional): Few loops state that they rank the full catalogue.} Of the ten offline-selecting loops that report ranking
metrics, three rank the full catalogue, three use sampled candidates and four do not say, so between three and seven
use full ranking. The three full-ranking loops are RankEvolve-HSTU, Population Evolution and the retrieval system of
Amazon's AutoResearch. Self-EvolveRec and RecHarness pair each test item with 99 sampled negatives, and we code RecEvolve as sampled. Amazon's agent also changed the candidate set during the campaign: a
text-only fallback ``expanded catalog coverage by 5.8$\times$''~\cite{chandran2026autoresearch}, so its earlier evaluations ranked a smaller candidate set than its later ones. Five offline-selecting loops evaluate ranking-stage CTR models with AUC
or a loss, as is standard for that stage (\S\ref{sec:threats}), and AutoLR selects offline but headlines only online lifts.

\paragraph{F2 (provisional): Half the offline loops do not state their selection data.} Of the 16
offline-selecting loops, eight do not say which data select candidates, four select on the data they report, and four name a validation split, so
between 4 and 12 select on the data they report (Table~\ref{tab:headline}). The four naming validation are Self-EvolveRec, RecHarness, VirtualMLE and EvoSkillRec. Of the four that select on the data they report, RankEvolve-HSTU's persistent leaderboard is the canonical full-test
NDCG@10~\cite{chen2026rankevolve}, and Amazon's AutoResearch ``retains modifications that improve a held-out scalar
metric'' and headlines the trajectory's peak~\cite{chandran2026autoresearch}. EvoPilot selects and reports on one
held-out replay set~\cite{fu2026evopilot}. Population Evolution selects on its source instances' evaluation scores
and reports its local gains on them, while withholding the transfer targets from the proposer; it also calibrates the
shared baseline configuration on the released test split~\cite{peng2026population}. All four disclose these choices,
which is to their credit. The eight silent loops are EvoRec, NOVA, AgentX-Model, AutoLR,
RecEvolve, Astar, A-MLE and Trajectories-to-Evidence. In all eight the keep decision is an offline score on unnamed
data, and all but A-MLE then A/B-test the
kept candidate as a confirmation.\footnote{The score is judged in AgentX-Model by an LLM, in A-MLE by a significance test against a rolling baseline followed by human
review, and in Trajectories-to-Evidence together with an LLM-assisted claim check.} Outside recommendation, the travel-search co-scientist keeps or
reverts each change on the same held-out metric that it reports~\cite{wu2026coscientist}.

\paragraph{F3 (provisional): Two of 16 offline loops state test-once use.} Of the 16 offline-selecting loops, two state that the selected
candidate was evaluated on held-out test data once after the search (RecHarness, VirtualMLE), six use the test data
during the search or repeatedly, and eight do not say, so between 2 and 10 are test-once. Of the six, four report on the data they select on (RankEvolve-HSTU, Population Evolution, Amazon, EvoPilot), so their F3 code follows from their F2 code and is not separate evidence. Only two of the six are coded no on other grounds:
AgentX-Model reports the best AUC over rounds and experiments, and EvoSkillRec scores every candidate on test in every
generation while stating that the scores are never used for selection.

\paragraph{F4: No loop reports spread over repeated sessions.} None of the 16 offline-selecting
loops repeats an evolution session and reports the spread, and seven have partial evidence. None of the ten online-selecting loops repeats a session for its headline result. Of the seven, RecHarness and VirtualMLE
average three runs without a standard deviation.\footnote{RecHarness does so on its Amazon datasets; it is not stated for KuaiRec.} Population Evolution reports one run per configuration, with repeated
evaluations of the reference score and unreported preliminary runs whose ``ordering was consistent''~\cite{peng2026population}. A-MLE re-runs a candidate when within-run variance is high, which the authors say ``materially
reduced'' single-seed promotions~\cite{gao2026amle}. AgentX-Model, EvoPilot and Amazon estimate the noise of single
models without repeating a session.\footnote{EvoPilot notes that two publications of the same model, configuration and pinned
data ``differed by 0.36 points''~\cite{fu2026evopilot}, and Amazon re-evaluates one model across 11 dates (``6.18\%
$\pm$ 0.28 pp'')~\cite{chandran2026autoresearch}.} Several papers state that their gains are within the resolution of
a single run: EvoSkillRec notes margins ``on the order of $10^{-4}$ AUC, which a single evolution run cannot reliably
separate from run-to-run variation''~\cite{li2026evoskillrec}. AgentX-Model reports standard deviations of
0.0010--0.0022 AUC over repeated runs with a fixed seed while counting an experiment as above baseline if it exceeds it by more than
$10^{-6}$~\cite{yang2026agentxmodel}. AutoLR, in its audited configuration, promoted candidates after a single run
with noise calibration disabled, a risk its authors name the ``KEEP ratchet'': each promoted model becomes the
baseline for all later comparisons~\cite{zhang2026autolr}. Among the online-selecting loops, Google runs six independent sessions with bracketed ranges, but only for an ablation. For these loops a repeat
is only practical on a replay (R4 in \S\ref{sec:protocol}).

\paragraph{F5 (descriptive): How loops check that selected gains transfer.} Of the 16 offline-selecting loops, one
checks its selected candidates on held-out data of the same task (EvoSkillRec), nine confirm a kept candidate online, five check on other data, scale, users or dates (Population Evolution, RankEvolve-HSTU, VirtualMLE, Self-EvolveRec, Amazon; Self-EvolveRec's held-out users are simulated, the weakest of the five) and one has none (A-MLE). EvoSkillRec's check is inconclusive: of five candidates on its validation Pareto front, only the one with the highest validation AUC keeps its gain on test, by a margin from a single run of the order F4 says a single run cannot separate from noise. All nine online confirmations report a gain, though only for the one candidate that reached traffic. The evidence of gains that do not survive comes from two sources. One is transfer across datasets and scale, which asks whether a gain generalises rather than whether the selection data were overfitted; the other is comparison points outside recommendation. In Population Evolution most locally selected ranking and RL candidates do not pass at larger scale~\cite{peng2026population}, and in EvoRank the gains of the first campaign ``were almost entirely fitness noise''~\cite{patel2026evorank}. None of this measures how much of the
published recommender gains is selection noise; it shows that the question cannot be settled without held-out checks. Appendix~\ref{app:details} gives the numbers.

\paragraph{F6 (descriptive): Comparisons against a null search.} Of the 16 offline-selecting loops, three compare against a non-LLM search at an equal or
larger trial budget (in any search space; Table~\ref{tab:codebook}), five have partial controls and eight have none. The three are VirtualMLE (grid search and Bayesian optimisation), NOVA (Optuna-TPE) and EvoSkillRec (NASRec, alongside OpenEvolve), and in all three the LLM loop is reported to win. Two of the nulls (VirtualMLE's and NOVA's) search the loop's own space, and only VirtualMLE's also at a total budget that includes the LLM cost (R5). No loop runs an equal-budget random search over its own edit space, and the two random policies we found were not dominated. The control matters because random
search with early stopping matched leading NAS methods~\cite{li2019randomnas} and classical optimisers beat LLM agents in fixed
hyperparameter spaces~\cite{ferreira2026hpo,rodrigues2026llmhpo}. Appendix~\ref{app:details} describes each control.

\paragraph{F7 (provisional): Four loops report shortcuts in their own evaluation.} Four of the 27 core
loops and one comparison point report metric-winning bugs, metric inflation or leakage in the loop's own evaluation (Table~\ref{tab:failures}). The agent introduced three of them (RecEvolve's in an exploratory session with the loop's own agent and evaluator); EvoPilot's is not attributed. None is reported as a headline gain. Where a paper says what caught a shortcut, it was a person (RecEvolve, Amazon) or the agent's diagnosis of anomalous results (RankEvolve-HSTU), not the keep-or-reject rule. That is expected rather than shown by three papers: a keep rule that scores the metric a shortcut inflates cannot reject it, so the check must sit outside the metric. Four incidents in 27 loops say little about how often shortcuts go unreported, since preventive guards (EvoRank's pre-search leakage audit~\cite{patel2026evorank}, NOVA's verifier~\cite{liu2026nova}) leave nothing to report. These papers should be credited for reporting (R8). The second coder also flagged AutoLR (Appendix~\ref{app:provenance}). Appendix~\ref{app:details} gives each incident and the isolation each loop states.

\paragraph{F8 (descriptive): How baselines, budgets and openness are reported.} Some large relative gains are measured against weak starting
points, few loops describe tuning their baselines, and budgets are reported in incompatible units. The 17 loops that report an online lift on a broad metric (one a whole surface is judged by) report from +0.052\% to +4.86\%. This counts a fresh confirmation where the paper reports one and otherwise the reported figure; taking Sortify's selecting round instead raises the upper end to +9.2\%. The range is descriptive, since metrics, designs and baselines differ, and it is the same without PILOT's non-randomised before/after lift and A/B Agent's selecting-round figure (Appendix~\ref{app:readings}). Only VirtualMLE and Amazon's AutoResearch describe tuning their
baselines, and only VirtualMLE says on which data (a third, Population Evolution, calibrates its baseline on the test split, so the lenient R7 proxy in Table~\ref{tab:pilot} counts three). Twelve of 27 report
LLM tokens or cost, four release code, two promise to, and six do not name the LLM they use. Appendix~\ref{app:details} gives the examples and the counting rules.

\paragraph{F9 (provisional): Online loops rarely correct across rounds or confirm afresh.} Nineteen of the 27 loops report online
experiments. Of the ten that select online, none corrects for multiple testing across rounds (one partially) and one confirms its chosen candidate afresh (four partially). The partial codes are unstable: a blind LLM re-coding (same model family as the extractor) gives the same totals but agrees on only two of the four partial loops. Online experiments are the main safeguard of the industrial loops and strong evidence when well designed. In nine loops that select offline, the A/B
test checks one candidate chosen beforehand, so it is a confirmation by construction. In the ten
online-selecting loops the experiment is the keep-or-reject rule, and there the headline effect is usually the
selected round, although the arm chosen as best overstates its effect~\cite{lee2018winnerscurse,berman2026winners}. Only Sortify re-tests its chosen round in a fresh
experiment~\cite{cheng2026sortify}. Across all 19, eight state the experiment duration and seven claim
significance or report confidence intervals for the headline result, but only three of them report an interval or a named test. Appendix~\ref{app:details} gives the partial cases and the counting rules.

\paragraph{Practices worth copying.} The audit also found reported practices that, if combined, would meet most of the
checklist in \S\ref{sec:protocol}; we did not test their effect. They are:
RecHarness's validation-only selection with a single test evaluation; VirtualMLE's
hidden test set, immutable pipeline, and grid-search and Bayesian-optimisation baselines; EvoSkillRec's validation-versus-test check of its
Pareto front; Population Evolution's withheld transfer targets; NOVA's leakage verifier and EvoRank's pre-search
leakage audit with an equal-budget random search; RankEvolve-HSTU's mandatory diagnosis of negative results; and
Sortify's fresh re-test and PILOT's pre-registered confirmation design.

\paragraph{Does selection really overfit?} A meta-analysis of 120 Kaggle competitions found little overfitting to
public leaderboards~\cite{roelofs2019metaanalysis}, and new test sets for ImageNet showed accuracy drops but preserved
model rankings~\cite{recht2019imagenet}, partly because similar models overfit a reused test set less than theory
predicts~\cite{mania2019similarity}. Agent-proposed candidates are near-copies of an incumbent, which by that argument
limits regressional overfitting. Two differences remain: an agent loop evaluates hundreds of correlated candidates on
one split without a resubmission cap~\cite{blum2015ladder} and keeps the maximum, and it controls the code that produces
the score, which no Kaggle team does. The direct measurements (F5) show that some selected gains shrink or vanish on
transfer across datasets and scale while others survive; the one same-task check settles nothing. The safe conclusion is not that self-evolving recommenders do not work. It is that, for gains selected and reported offline, the
published evidence cannot yet tell how much is real. An online confirmation is direct evidence for the one candidate that reached traffic. For the online-selecting loops, whose A/B gate is direct evidence, the open question is the selection across rounds (F9).

\section{A Proposed Reporting Checklist}\label{sec:protocol}
%=====================================================================

We argue, rather than show, that most of the problems are cheap to report: what the audit finds missing is mostly a statement of what was done, not a new experiment (Appendix~\ref{app:exemplars} applies the minimum tier to two papers). Table~\ref{tab:checklist} turns the codebook into a proposed reporting checklist. Each item has a minimum that any
paper can meet by reporting what it already did, and a recommended practice that costs compute. Each maps to the
audit criterion that checks it, so that a paper's compliance can be read off the same coding. The items extend
general checklists for NAS research~\cite{lindauer2020bestpractices}, ML-based science~\cite{kapoor2024reforms} and
agent benchmarks~\cite{zhu2025abc} to the specific failure points of an evolution loop (Figure~\ref{fig:loop}).
Several items are established practice restated for loops: R1 follows the recommender-evaluation literature on sampled
metrics~\cite{krichene2020sampled}, R4 the reporting of seeds and variance in deep RL and NLP~\cite{henderson2018deeprl,
agarwal2021precipice,dodge2019showyourwork}, R5 the random-search baseline of the NAS checklist~\cite{lindauer2020bestpractices},
R6 cost-aware agent evaluation~\cite{kapoor2025agentsmatter}, and R9 the practice of trustworthy online
experiments~\cite{kohavi2020trustworthy}. What is specific to self-evolving systems is that each item applies to a
\emph{chain} of selection stages and to an optimiser that can change its own measurement. R2 asks for the selection
signal at every stage, not for one split. R4 counts evolution sessions, not training seeds. R5 asks for a null over the
loop's own edit space, and R8 asks what the agent can read and write. R9 does not ask for a correction across a platform's independent launches, which are usually governed one launch at a
time with guardrails or false-discovery control. It addresses the case where one loop picks the best of its own rounds and
reports that round's effect, which the winner's curse biases upward~\cite{lee2018winnerscurse}; the remedy is a correction
across those rounds or, more simply, a fresh confirmation whose effect is the one reported. Appendix~\ref{app:exemplars} applies the minimum tier to two audited
papers (a core loop and a learning-to-rank comparison point). Table~\ref{tab:pilot} reads the audit coding as a retrospective proxy for the checklist; this is a check by
the authors on codes recorded for another purpose, not an application of the checklist by independent raters, and its
R1, R2, R6 and R8 proxies are lenient. \emph{We therefore estimate no rate of compliance with the minimum tier.} Most
papers state some budget (R6); the R2 and R8 proxies are met mostly by construction (the online gate; bounded actions). Few say
how their baselines were tuned (R7) or report both duration and an interval or significance test for their online result (R9). For R3, R4
and R5 the coding records only the recommended practice, which almost no paper follows. Stricter readings of each item are in Appendix~\ref{app:exemplars}.

\paragraph{Cost of compliance.} The minimum tier only asks authors to report what they did, so it costs little beyond
writing. Industrial authors may be unable to disclose some items, such as traffic shares or the exact data
split; they can then say that an item is withheld rather than leave it unstated. The minimum tier does not make a weak design acceptable, but it makes it visible. In the recommended tier, R4 and R5
multiply training cost: three sessions plus one equal-budget null cost four sessions. For an academic harness such
as RecHarness, whose budget is 43{,}200 GPU-seconds per backbone~\cite{ling2026recharness}, that is 48 GPU-hours per
backbone. LLM costs are small next to training: VirtualMLE reports \$1.5--4.8 of LLM cost per
session~\cite{cao2026virtualmle}, EvoRank about ten dollars for fifty iterations~\cite{patel2026evorank}, and NOVA
about \$29 per task, or about \$22 with cached artifacts~\cite{liu2026nova} (LLM cost only). For industrial loops whose candidates take hundreds of
GPU-hours~\cite{li2026autorecsys}, R4 and R5 can be applied to a replay or a reduced-scale proxy, as AgentX-Model
does for scheduling policies~\cite{yang2026agentxmodel}, while R9 governs the launch decision.

\paragraph{A shared protocol.} Several items can be enforced in software rather than requested in prose: a sealed
test split (R2, R3), a single final evaluation, an equal-budget null evolver (R5), a budget card (R6) and an
evaluator outside the agent's reach (R8). Appendix~\ref{app:recforge} describes recforge~\cite{recforge}, a
reference implementation that we are building. It enforces R2, R3 and R5 through its API but not yet R8, and its seal holds
only against code that uses the API. Its current protocol is leave-one-out, and we report no results from it.

\section{Open Problems}\label{sec:open}
%=====================================================================

\paragraph{Isolation without crippling the agent.} Code-level agents need to read data and change training code, and
that is exactly the access that lets them leak targets or change what the metric measures (F7). Verification gates
(NOVA), fixed evaluation code (AgentX-Model), immutable pipelines (VirtualMLE) and cross-agent review (RankEvolve-HSTU) each
close part of the gap. A principled design would give the agent a process that physically cannot reach evaluation
labels or code, and would audit every metric-relevant change, such as batch size for in-batch metrics.

\paragraph{Proxies for expensive candidates.} Industrial candidates take hours to hundreds of GPU-hours, so loops screen
on proxies: small decoders~\cite{nian2026semanticindex}, data subsets and peer datasets~\cite{peng2026population},
training-loss curves and learned reward models~\cite{hu2026astar}, and LLMs can themselves predict a candidate
architecture's performance before training~\cite{jawahar2024llmpp}. The evidence shows that proxy fidelity depends on
what is evolved. Characterising when a proxy can be trusted, and spending budget to re-check proxies during search, is
open.

\paragraph{Budget-normalised comparison of evolvers.} There is no common unit of cost and no common task, so the field
cannot say whether bandit routing, island evolution, research-agent pairs or learned proposers are better. A shared
benchmark with a budget card (R6) and an equal-budget random baseline (R5) would allow the first such comparison.

\paragraph{Evolving generative recommenders.} Semantic-ID construction, codebook collisions, constrained decoding and
preference-alignment losses are new design dimensions with little human prior and large effects. They are natural
targets for code-level evolution, and almost untouched (\S\ref{sec:systems}).

\paragraph{From offline wins to online value.} RecEvolve observes that offline evaluations often show ``win-win''
results while online tests show trade-offs~\cite{pan2026recevolve}. Loops that select on offline metrics inherit the
gap, and loops that select on online experiments face multiple testing and slow iteration. A starting point is to combine the two with a fresh
online confirmation of the final candidate, ideally pre-registered, as Sortify does with a seven-day re-test.

\paragraph{Circularity at the policy level.} L4 systems are often judged by simulators from the same model family as the
agent being improved. Held-out simulators~\cite{kim2026selfevolverec}, verifiable rewards~\cite{narasimhan2026taurec}
and reward-model benchmarks~\cite{zeng2026recrmbench} are partial answers.

This section collects the limits of the audit in one place; Table~\ref{tab:whocoded} summarises who coded each
part and how it was checked.

\paragraph{Coverage.} Our cut-off is 22 October 2026, and we coded the arXiv version available on that date. Generic
keyword search performed poorly, so coverage relies on citation-graph search, with titles screened by one screener,
and may miss systems that neither cite nor are cited by the core set. A recall check within that network, run with an
LLM agent on 27 October, found 22 of 24 cited candidate systems named in the survey, but it is not independent of the
search. The first sweep missed five of the 27 core loops and four more were recognised only after coding, so the
corpus is not saturated. 32 of the 34 loops we found are from 2026, but our arXiv screen began in 2025, so the field may be
older than the corpus suggests (Appendix~\ref{app:provenance}). Six known in-scope systems are not coded; adding them
could move any core count by at most six (Table~\ref{tab:headline}).

\paragraph{Coding.} Two authors coded the scored criteria and the incident flag, not independently, so the evidential
weight is closer to one careful coder with a consistency check than to double coding. The first coded from verbatim
quotes extracted by LLM agents and checked against the paper text. The second coded the full texts by hand, without an
LLM by the coder's own account, from a guide written by an author who knew the corpus. The first coding's files were in
the shared repository throughout, kept from the second coder only by the guide's instruction, and 17 of its cells,
among them all four incident codes, were visible in the codebook file, so agreement before reconciliation is likely
inflated. Criterion-stratified $\kappa$ (chance agreement taken within each criterion) is 0.68 (95\% interval
0.55--0.77) over the 16 offline-selecting loops and 0.71 (0.60--0.79) over all 243 cells; C5 (0.25), C6 (0.54) and C8
(0.56) are the weakest. Of the 38 disagreements, 31 were resolved to the second coding under rules written during
reconciliation, so $\kappa$ is not the reliability of the released codes. F9's online items were coded by one author on
27 October, after the cut-off, and checked by a blind re-coding with an LLM of the same family as the extractor.
Appendix~\ref{app:provenance} gives the alternative statistics, batch timing, guide changes and the cells that rest on
reconciliation; every change to a cell is in the released changelog.

\paragraph{What the counts can and cannot say.} ``Not stated'' does not mean ``not done'': authors may have followed a
practice without reporting it, and a loop coded ``not stated'' may well have been evaluated soundly. The findings
describe what the coded arXiv versions report, not the quality of the deployed systems. Offline hygiene criteria mean
little for loops whose keep-or-reject decision is an online experiment, which is why those loops are assessed on the
design of their experiments (F9). The audited authors have not yet verified their rows. We will maintain the audit as
a living table: new systems will be coded with the same codebook and second-coded, each update will be a versioned,
archived release with a cell-level changelog, and corrections from authors will be accepted with a quote from their
paper and checked by a second coder. A correction to a cell coded not stated moves a count only within its stated
range (F2 between 4 and 12, F3 between 2 and 10); a correction to a cell coded yes or no can move it outside.

\paragraph{Conflict of interest.} The authors are building recforge, the reference implementation described in
Appendix~\ref{app:recforge}. The audit does not depend on it, but recforge enforces R2, R3 and R5 of the checklist, so
we have an interest in the checklist's adoption. It has produced no evolver results, and its isolation is API-level only. One of us wrote the ideation-harness study cited in
\S\ref{sec:systems}, which is outside recommendation and not peer reviewed, and both of us wrote the LLM-guided
regularisation paper cited in \S\ref{sec:method} as an excluded example.

\section{Conclusion}
%=====================================================================

In the papers we found, nearly all from 2026, self-evolving recommenders range from research prototypes to loops
that their authors report in production at many large platforms. The loops are inventive, and many report online gains from production A/B tests.
Their offline evidence is sparsely reported: of 16 offline-selecting loops, 8 do not state their selection data, 2
state test-once use, and none reports spread over repeated sessions. Null searches at an equal or larger trial budget
are rare, and whether selected gains transfer cannot be told from the corpus. Online gates are reported but seldom
corrected for the rounds they test or confirmed afresh. Four loops report shortcuts in their own evaluation; where a
paper says what caught one, it was a person or the agent's own diagnosis, which is what to expect when the keep rule
scores the inflated metric. Guards outside that metric are therefore needed. These are counts of what the papers
report, coded by the authors (\S\ref{sec:audit}), and an outside re-coding is the next check. We expect, but have not
shown, that most of what is missing is cheap to report. We hope that the checklist in Table~\ref{tab:checklist}, the
released audit and design data, and protocols that enforce the checklist in software make it the norm, so that the
next comparison of evolvers can be made on equal terms.

named as borderline, adjacent or uncoded, and the two then absent, cited here since, are borderline at most---MoFA, a one-shot

The second sweep counted only hits not already in the corpus, so it did not re-examine them: they show a classification miss rather than a search miss. Six known systems in scope are not coded, four recognised too late for the coding and two

\section{Details of Findings F5--F9}\label{app:details}

This appendix gives the evidence and counting rules behind findings F5--F9 of \S\ref{sec:audit}, which the main text
states in brief.

\paragraph{F5.} In EvoSkillRec, five candidates lie on the validation Pareto
front, ``but only P1 (round 19) retains both improvements on the test set''~\cite{li2026evoskillrec}; P1 has the
highest validation AUC of the five (0.92999 against 0.92927--0.92996),\footnote{The paper's Table 4, transcribed with all five rows in the released design evidence.} so choosing among the front points by validation would have picked it, although the paper states no rule for
choosing one.\footnote{A candidate off the front with higher validation AUC failed an eligibility constraint.} P2 and P3 lose their AUC gain on test, and P4 and P5 have none on validation. This is the only same-task
validation-to-test check in the core corpus, and both coders coded it yes. But
the front has two objectives and no stated selection rule, and P1's validation gain over the baseline, $5.1\times10^{-4}$ AUC (0.92999 against 0.92948), shrinks on test to about $1.8\times10^{-4}$ AUC from a
single run, of the order the paper says a single run cannot separate from run-to-run variation (F4), so the check
shows neither that the selected gain is real nor that it is not. Of the other fifteen, fourteen are coded partial and A-MLE no.\footnote{Online confirmations are coded partial by a reconciliation rule; see Appendix~\ref{app:provenance}.} All nine online confirmations report a gain, which shows that the selected candidate carries over to traffic, though only for the one candidate that reached it. The evidence of
gains that do not survive comes from transfer across datasets and scale, which asks whether a gain generalises rather
than whether the selection data were overfitted, and from comparison points outside recommendation. Population Evolution checks transfer across datasets and scale: a ranking candidate gains 10.66\% on a peer dataset and loses 0.79\% at
larger scale, two of three peer-screened designs keep their gains, and sharing evidence across searches raises the
larger-scale pass rate for ranking from 11/60 to 18/60 and for RL from 0/15 to 2/12~\cite{peng2026population}:\footnote{For watch-time it rises from 4/10 to
5/7.} in ranking and RL, most locally selected
candidates do not graduate. Two other loops carry selected recipes or memories to other data, without a larger-scale step: RankEvolve-HSTU replays its recipes on four further datasets, one run each, and in Trajectories-to-Evidence three of five memory transfers help and one hurts~\cite{chen2026rankevolve,zhuang2026trajectories}. Two further observations suggest that headline values are optimistic. Amazon's headline lift of 1.82$\times$ is the peak of a
trajectory, ``${\sim}$2.6$\sigma$ above the across-date mean'' of 1.63$\times$~\cite{chandran2026autoresearch}, and
Kuaishou's trajectory analysis finds that for 22 of 30 methods the last round falls below an earlier
best~\cite{zhuang2026trajectories}. The comparison points give larger and mixed effects: in EvoRank, the gains of the first
(loss-evolution) campaign ``were almost entirely fitness noise'' on 60k held-out queries, while about 70\% of the
second campaign's gains survived~\cite{patel2026evorank}; in an e-commerce search loop, effects on a shadow-traffic
proxy were 17 and 29 times larger than in decision-grade online experiments for the two candidates traced, on
different metrics per stage, and five promoted candidates
showed no significant gain~\cite{wang2026pear}; and in Evolving Semantic Indexes, a proxy decoder that ranks
semantic-ID programs well (Spearman $\rho = 0.90$) becomes ``not only less informative but misleading'' once the
training objective may change, on a small sample of five programs~\cite{nian2026semanticindex}. A controlled study
shows that the mechanism exists: on a label-permuted task with no real signal, a coding agent given exact validation
scores ``ended by reporting a gain of 0.0157''~\cite{yao2026feedbackcontract}.

\paragraph{F6.} The three null searches differ in scope.\footnote{NOVA's Optuna-TPE runs at a matched trial

The partial controls are NAS baselines at unmatched budgets, a random arm router that still uses LLM edits, a
replay-only random policy, or a starting model tuned by an optimiser that the LLM partly steers;
comparisons with human workflows or with other LLMs do not count. No loop runs the catalogue-of-known-techniques null of \S\ref{sec:kept}. The two random policies we found were not dominated, although neither is a null over a whole loop: in AgentX-Model's historical replay, which randomises the choice of experiments rather than the edits, in
Scenario A ``Uniform Random's mean exceeds Fixed, Greedy, and Joint'' policies, and no policy led consistently across
scenarios~\cite{yang2026agentxmodel}; in
EvoRank's loss campaign an equal-budget random search transferred as well or better ($p=0.03$)~\cite{patel2026evorank}.

matched trial budget''~\cite{zhang2026autolr}. The history of architecture search explains why the control matters: random
search with early stopping matched leading NAS methods~\cite{li2019randomnas}, the search phase of several methods was no

hyperparameter spaces~\cite{ferreira2026hpo,rodrigues2026llmhpo}. The online-selecting loops compare each candidate with a

\section{Catalogue of Systems}\label{app:catalogue}

\subsection{Configuration-level loops (L1)}
L1 systems let an LLM change numbers or switches while the model code stays fixed. VirtualMLE tunes SASRec and HSTU
over a predefined action space of hyperparameters and pre-implemented structural switches (so its kept architecture options, such as relative position bias or a SwiGLU feed-forward block, are switch settings, not code the agent writes) through an execute--reflect loop with a hierarchical memory that transfers across datasets~\cite{cao2026virtualmle}.
In production, CORAL allocates retrieval budgets and serving treatments~\cite{azhar2026coral}, AgenticRecTune tunes
fusion weights and thresholds across pre-ranking, ranking and re-ranking~\cite{wu2026agenticrectune}, Sortify
searches the exchange rates of a sorting formula with Optuna~\cite{akiba2019optuna} while an LLM meta-controller recalibrates the search's
offline-to-online transfer intercepts and penalties~\cite{cheng2026sortify}.
GEARS selects segment-level treatment policies~\cite{yun2026gears}, and SR-Agent edits post-ranking diversity and
exposure strategies through four bounded action types~\cite{yang2026sragent}. Taobao's PILOT has LLM roles choose
ranking-objective weights for user segments from a legal-command envelope generated by deterministic
services~\cite{pilot2026}; Kuaishou's A/B Agent iterates strategy parameters across online rounds with a hierarchical
experience tree~\cite{jiang2026abagent}; and DMRL trains a small LLM with RL to rewrite the skill
document that an ad-tuning agent follows~\cite{zhang2026dmrl}. LLM-driven hyperparameter optimisation~\cite{zhang2023llmhpo,liu2024agenthpo} is the general-ML form of L1 and is
routinely compared against Bayesian optimisation or random search, the null control that few recommender loops run
(F6). Most L1 systems in production select directly on online experiments; an e-commerce search loop adds a multi-fidelity ladder from shadow-traffic proxies to
decision-grade online tests~\cite{wang2026pear}.

\subsection{Code-level loops in the open (L2)}
\textbf{Self-EvolveRec}~\cite{kim2026selfevolverec} runs an AlphaEvolve-style loop over the whole pipeline code of
NCF~\cite{he2017ncf}, NGCF~\cite{wang2019ngcf}, SASRec and MoRec~\cite{yuan2023morec} seeds; besides validation metrics it receives directional critiques from an LLM user
simulator and from a diagnosis tool that evolves with the model. \textbf{RecHarness}~\cite{ling2026recharness} routes
each round with Thompson sampling over human-defined ``edit arms'' (schedules, dropout, depth, pooling, features,
loss) plus ``jump'' arms for structural changes, uses validation feedback only, evaluates the incumbent on test once,
and caps compute at 43{,}200 GPU-seconds; HSTU is one of its five backbones. \textbf{EvoSkillRec}~\cite{li2026evoskillrec}
evolves architectures as typed ``skill genomes'' of executable modules and promotes validated modules into a skill
library. \textbf{RankEvolve-HSTU}~\cite{chen2026rankevolve} composes Claude Code and Codex under an executable operating
protocol in which the two agents review and repair each other's edits to HSTU, and introduces ExecML-HSTU, a benchmark
of how often agent edits are executed correctly. \textbf{Population Evolution}~\cite{peng2026population} runs several
evolution searches that share evidence across related datasets, screens candidates on peer datasets (and, for LLM and VLM targets, on small training subsets), and promotes
survivors to larger scales; it introduces RMD-Bench. AutoRecLab~\cite{baumgart2026autoreclab,beel2025autoreclab}
generates recommender experiments from natural-language descriptions; it automates experimentation rather than
evolving a model, and we do not audit it. Two loops evolve data and features rather than the model: RuleAgent has a
language agent propose rules for denoising implicit feedback, retrains with an unlearning shortcut, and keeps rules by
validation performance~\cite{wang2025ruleagent}, and Agent0 tunes the prompts that turn raw text into categorical
features through feedback from a downstream oracle~\cite{skrlj2025agent0}.

\subsection{Code-level loops in industry (L2)}
Most industrial systems share a two-stage design: an offline loop screens agent-written candidates, and online
experiments decide launches. Google's loop for YouTube ranking~\cite{wang2026selfevolving} has Gemini personas
propose optimiser, architecture and reward changes, promotes on validation loss (with a proxy metric for reward changes) and then on north-star A/B
metrics, and reports LLM costs of about \$20{,}000 over six months. RecEvolve~\cite{pan2026recevolve} runs the full
research loop on a production two-tower retrieval model. Meta's REA plans, launches and debugs ads-ranking
experiments with up-front GPU budget approval~\cite{meta2026rea}; A-MLE explores a portfolio of ads-ranking models
with human checkpoints~\cite{gao2026amle}; Auto-RecSys runs idea- and execution-evolution loops over multi-day training
jobs~\cite{li2026autorecsys}; and RankEvolve-HSTU and Population Evolution above also come from Meta. Alibaba's
EvoRec~\cite{mu2026evorec} pairs research and code agents with a skill evolver, and Astar~\cite{hu2026astar} trains an
8B model on the commit history of an advertising system to propose the next evolution direction. From Astar's
authors, AutoModel organises an industrial recommender as evolution agents for models, features and online
experimentation, with a case study of reproducing published methods and comparing them offline against
production~\cite{zhang2026agenticrs}. AgentX, deployed at Kuaishou~\cite{lao2026agentx}, iterates online strategies and model research, and its successor
AgentX-Model~\cite{yang2026agentxmodel} runs research lineages (reproduce, follow up, compose, diagnose) over production
rankers. A further Kuaishou paper converts research-agent trajectories
into auditable evidence~\cite{zhuang2026trajectories}. Tencent's NOVA~\cite{liu2026nova} adds verification gates that
reject recommender-invalid edits such as target leakage, NetEase's AutoLR~\cite{zhang2026autolr} reviews proposals with
a multi-expert proposal council under a limited trial budget, and Tencent's RecSys Factory bounds agent autonomy to typed decision points
in fixed pipelines~\cite{ao2026recsysfactory}. A Trip.com co-scientist for travel search ranking~\cite{wu2026coscientist},
LLM evolution of learning-to-rank pipelines (EvoRank~\cite{patel2026evorank}) and of lexical retrieval
functions~\cite{nian2026rankevolveir} are close relatives outside recommendation. Meta's EvoPilot runs a
37-day campaign of agent-proposed configuration and retraining changes to video-retrieval models behind a fail-closed
verifier and catalogues the failures it met~\cite{fu2026evopilot}, and Amazon's AutoResearch rewrites the training code
of a book-retrieval model and tunes a semantic-ID tokenizer in a twelve-week campaign of more than 220 experiments, naming the failure modes it
met~\cite{chandran2026autoresearch}. Adjacent loops evolve ads kernels~\cite{kernelevolve2025}, off-policy-evaluation
code~\cite{wu2025growthhacker}, search-relevance models~\cite{wang2026serm} and an LLM policy layer trained against a
learned evaluator~\cite{zhang2026dream}, and an operations agent for Kuaishou's search engine evolves its skills
from on-call engineers' corrections~\cite{liu2026bianque}. Feature-engineering loops are close relatives: an
error-driven loop turns AUC ranking inversions into feedback for an LLM feature generator~\cite{barlier2026feature}, a
planner-guided agent writes feature code for recommendation models with human checkpoints~\cite{thakur2026feature}, and
LATTEArena compares LLM feature-engineering methods on cost as well as accuracy~\cite{hao2026lattearena}.

\subsection{Components of generative recommenders (L3)}
Generative recommenders expose objects that do not exist in ID-based models. Evolving Semantic Indexes, a generative
document-retrieval system that we treat as a comparison point, runs
LLM-driven program evolution over semantic-ID construction, collision handling, decoding and the generator's training
objective, using a one-million-parameter proxy decoder as fitness~\cite{nian2026semanticindex}. AgenticTagger has an
LLM refine a hierarchical item-descriptor vocabulary used as tokens~\cite{xie2026agentictagger}, and a generative
recommender can reassign its own item tokenisation during training~\cite{chen2024tokenization}. Amazon's
AutoResearch is the only loop in our corpus that edits a production-scale semantic-ID tokenizer, and the only one in which the agent
gamed a tokenizer metric~\cite{chandran2026autoresearch}. Feedback-grounded
policy discovery distils LLM-discovered natural-language policies into a semantic-ID generator~\cite{chen2026policydiscovery}.
Evolving Semantic Indexes evolves TIGER-style semantic-ID components for document retrieval but releases no code;
no open system yet does so for recommendation under a shared protocol.

\subsection{Adjacent work: self-improving agentic recommenders (L4)}\label{sec:l4}
When the recommender is itself an LLM agent, the evolving object is its memory, skills, prompts or weights, and the
feedback is mostly generated by the system. We catalogue this line as adjacent work and do not audit it
(\S\ref{sec:method}). Memory and reflection methods update user and item agents
(AgentCF~\cite{zhang2024agentcf}, AgentCF++~\cite{liu2025agentcfpp}), per-user policy
skills (SAGER~\cite{tao2026sager}), propagation modules optimised with textual gradients (RecNet~\cite{li2026recnet}),
and structured memories that are rewritten as interactions arrive (AtomRec~\cite{hu2026atomrec},
AMEM4Rec~\cite{nguyen2026amem4rec}, STEAM~\cite{liao2026steam}, MARS~\cite{shen2026mars}, MemRec~\cite{chen2026memrec}). Others build hint bases by reflection (Re2LLM~\cite{wang2024re2llm}), refine per-user
rubrics from user feedback (RecPilot~\cite{ou2026recpilot}), or let recommendation and user agents refine
each other's inferences over rounds without amplifying popularity or position bias~\cite{cai2024afl}. CoVeMem instead replaces rewritten text memory
with frozen collaborative-filtering states learned by gradient training~\cite{chen2026covemem}.
Weight-level self-improvement includes OneRec's alignment on its own samples, first by iterative
DPO~\cite{deng2025onerec} and then by on-policy RL~\cite{zhou2025onerectech,zhou2025openonerec}, self-play debiasing (SPRec~\cite{gao2024sprec}) and RL against a recommender's metric
(Rec-R1~\cite{lin2025recr1}). It also includes co-evolving recommender and user agents (CoARS~\cite{wang2026coars}), reasoning primitives and a teacher updated from a
student's on-policy outcomes (EvoReason~\cite{zhuang2026evoreason}), and recursive
self-training on filtered synthetic sequences~\cite{zhang2026rsir,hasan2026darsir}, where progress can also sit in earlier
generations, not only in the latest model~\cite{xu2026stateretention}. RecPrompt iteratively rewrites a news recommender's prompt with an
optimiser~\cite{liu2023recprompt}, and Spotify improves a conversational
recommendation agent's prompts, few-shot examples and tool descriptions with a coding agent, evaluated by an LLM judge
on synthetic conversations~\cite{palumbo2026spotify}. Simulated environments and benchmarks for such agents include
RecoWorld~\cite{liu2025recoworld}, the user simulators Agent4Rec~\cite{zhang2023agent4rec} and
RecAgent~\cite{wang2023recagent}, and the verifiable $\tau$-Rec benchmark~\cite{narasimhan2026taurec}. A controlled pilot found multi-agent recommendation
pipelines not uniformly better than a single-shot baseline~\cite{maragheh2025future}, a reminder that L4 gains also need
controlled baselines.

\subsection{Evolving the evolver (meta)}
Eleven of the 27 audited loops change their own proposer. AgentX's SGPO applies semantic-gradient updates to its
agents' instructions and validation rules~\cite{lao2026agentx}. EvoRec, AgenticRecTune and EvoSkillRec grow skill
libraries from experiment outcomes~\cite{mu2026evorec,wu2026agenticrectune,li2026evoskillrec}, Auto-RecSys rewrites
execution playbooks~\cite{li2026autorecsys}, and VirtualMLE and PILOT carry tuning rules or methodology across datasets and
experiments~\cite{cao2026virtualmle,pilot2026}. Astar retrains its proposer on each iteration's verified
outcomes~\cite{hu2026astar}. NOVA turns confirmed semantic errors into verification rules and may commit validated
rules to its knowledge base for later tasks~\cite{liu2026nova}. AgentX-Model's agent proposes repairs to its own tools
and instructions, deployed only after human approval~\cite{yang2026agentxmodel}, and DMRL trains a small LLM with RL to rewrite the skill document
that an ad-tuning agent follows~\cite{zhang2026dmrl}. These are the recommender counterparts of harness
optimisation~\cite{lee2026metaharness,xu2026harness2,lou2026autoharness}. Outside recommendation, AIDE$^2$ keeps changes
to its own code that perform best on hidden evaluations and shows that they transfer to four held-out
benchmarks~\cite{srikanth2026aide2}; separating selection tasks from held-out tasks is what the meta-evolving
recommenders do not yet report. Meta-evolution inherits the selection
problem one level up: the harness is kept or discarded by a score of its own. Optimising against a learned or LLM judge
overfits the judge~\cite{gao2023overoptimization}, and a pre-registered study of LLM research-ideation harnesses by one
of us, outside recommendation and not peer reviewed, reports the same at the harness level: a harness optimised against
an LLM judge raised the judge's scores while the share of its hypotheses that held under measurement
fell~\cite{yang2026ideationgoodhart}.


\section{Alternative Readings of Individual Cells}\label{app:readings}

The findings in \S\ref{sec:audit} state each count under the released coding. The readings below would change a count;
each stays within the range given in Table~\ref{tab:headline}, except where stated.

\begin{itemize}
\item \emph{F1, RecEvolve's candidate set.} RecEvolve does not describe its candidate set with its evaluation, but states, in describing its batch-size incident (F7), that ``the Two-Tower model utilizes in-batch negative sampling''. If this is not taken as a statement of the evaluation protocol, RecEvolve's candidate set is not stated and the upper bound is eight; the released code, F1, Figure~\ref{fig:auditbars} and the R1 proxy (Table~\ref{tab:pilot}) all take the sampled reading, as the second coder did; the first coder coded it not stated.
\item \emph{F1, Amazon's catalogue.} Reading Amazon's ranking as not full gives two to six full-ranking loops.
\item \emph{F2, Google and Astar.} Google's loop also ranks candidates by validation loss, but online experiments decide which run and launch, so we count it as online-selecting; Astar's loss-decrease rule labels its training data and defines its success rate, but the paper does not say what decides its production iterations.
\item \emph{F2, Population Evolution.} Population Evolution's code is the least certain: an early verification pass read its test-split sentence as baseline calibration only and coded its selection data not stated; under that reading this count is three, the not-stated count nine, and F3's six loops coded no become five (F3's count of two is unchanged). The cell was changed during internal review and was among those visible to the second coder, so the coders' agreement on it is not independent (Appendix~\ref{app:provenance}).
\item \emph{F2, AgentX-Model.} AgentX-Model reports ``the highest measured AUC'' over its rounds, so its reported number is its selection statistic and its C3 is no (the evaluation is used repeatedly), but it never names the data that AUC is measured on; C2 asks which data select, and both coders coded it not stated. Amazon, coded as selecting on reported data, names them (``a held-out scalar metric''). Reading AgentX-Model's reported AUC as naming its selection data gives seven not stated and five on reported data, within the stated range, and R2 19 of 26.
\item \emph{F3, EvoSkillRec.} We code it ``no'' under the codebook's literal wording, test data used during the search or repeatedly, as the second coder did; the first coder and the drafted resolution read it as test-once, because the scores are not used, and that reading gives three (Table~\ref{tab:headline}, Appendix~\ref{app:provenance}).
\item \emph{F3, Self-EvolveRec.} Self-EvolveRec reports a ``Peak'' iteration, which suggests reporting the best score over iterations; it is coded not stated because the paper does not say which data that score is on. Reading it as no would move one loop from not stated to no and lower F3's upper bound to nine; the count of two is unchanged.
\item \emph{F5, VirtualMLE.} VirtualMLE reports validation and test N@10 for its selected configurations but states that the two are ``not directly comparable'', so we code it partial; counting it would make the count two.
\item \emph{F6, the null's search space.} EvoSkillRec's NASRec searches architectures rather than EvoSkillRec's own code-and-skill space; requiring the null to search the loop's own space gives two, and also requiring a total budget, LLM cost included, at least the loop's gives one (VirtualMLE).
\item \emph{F7, the incident count.} The incident code counts a shortcut in a candidate's evaluation inside the loop whoever introduced it; counting only those the paper attributes to the agent gives three. RecEvolve's arose in a separate exploratory session rather than in the reported runs; we count it because it arose in the loop's own evaluation of a candidate, and without it the count is three (two attributed to the agent).
\item \emph{F8, the lift range.} The range leaves out AutoLR (summed lifts only) and GEARS (anonymised metrics; its Metric~1 lifts would lower the floor to +0.011\%); its lower end is DMRL's main-table value (other tables go down to +0.021\%). Without RecEvolve's user satisfaction and EvoPilot's GSRR, the two metrics least clearly broad, or without PILOT's non-randomised before/after comparison and A/B Agent's selecting-round figure, the range is the same over 15 loops.
\item \emph{F9, borderline online-selecting loops.} Without GEARS, which makes one selection pass per experiment (\S\ref{sec:designs}), the F9 counts are 0 of 9 (1 partial) and 1 of 9 (3 partial); without GEARS, CORAL and DMRL, which have no explicit keep/reject rule, 0 of 7 (1 partial) and 1 of 7 (2 partial).
\end{itemize}

\section{recforge: A Reference Implementation}\label{app:recforge}

recforge~\cite{recforge} is an open benchmark that we are building to enforce the parts of the checklist that
software can enforce. It is under development, it has produced no evolver results, and the audit does not depend on
it. Its design follows the audit (Figure~\ref{fig:protocol}).

\input{figs/protocol}

\begin{itemize}
\item \emph{One protocol per version.} The current protocol is leave-one-out per user (last item test,
second-to-last validation) with full-catalogue ranking, the user's history removed, and HR and NDCG at 10 and 20
and MRR@100 (items ranked below 100 score zero). Leave-one-out ignores the global timeline and can leak future
information~\cite{ji2020leakage,hidasi2023flaws}; a global temporal split is the next protocol version. Results from
different versions are never put in one table, and every result is keyed by the source hash of the method, its
configuration and the code commit.
\item \emph{A sealed test at the API level.} Method code runs in its own process and receives only a training view;
asking for a validation or test target raises an error, and the method returns ranked lists that the parent process
scores. The seal holds only against code that uses the API: sealed scores and session state are ordinary files, so
an agent with file-system access could read test scores or alter the budget. A container mode that would close this
gap (R8) is planned, not implemented.
\item \emph{Budgeted evolve sessions.} A session has a trial and time budget. Each trial returns validation metrics
only; test metrics are computed and sealed. A single \texttt{finalize} reveals the test metrics of exactly one
trial, publishes it with the session's budget, and closes the session.
\item \emph{Evolvers on equal terms.} An equal-budget random search (the R5 null), a wrapper for an external coding
agent, and an OpenEvolve adapter drive sessions through the same interface, and each run reports the
validation-to-test gap of its finalized trial. They are tested on synthetic data only; the OpenEvolve adapter has
not been run end to end.
\item \emph{Baselines and data.} Popularity, ItemKNN~\cite{sarwar2001itemknn}, BPR~\cite{rendle2009bpr},
SASRec~\cite{kang2018sasrec}, HSTU~\cite{zhai2024hstu} and TIGER~\cite{rajput2023tiger}, with
MovieLens-1M~\cite{harper2015movielens}, Amazon 2014 Beauty, Sports and Toys~\cite{mcauley2015amazon}, MIND
news~\cite{wu2020mind}, and the OpenOneRec release~\cite{zhou2025openonerec}.
\end{itemize}
Not yet implemented: the container mode, recording of LLM tokens and cost, automatic aggregation of repeated
sessions, and the temporal split.
